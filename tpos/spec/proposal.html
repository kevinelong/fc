3 · Data & Persistence — Tenant Isolation

Requirements echoed. Spec §12 (strict per-tenant isolation at the data layer, provable by an automated negative test), Appendix A (logical data dictionary), Appendix B.5–B.6 (isolation outcomes; audit log, consent records, residency, retention), Appendix C (import idempotency), Appendix D (five date clocks, cost components).

The reference DDL is schema.sql — PostgreSQL 15+, generated from Appendix A and kept reconciled with the later appendices. The isolation mechanism, in depth:

Defense in depth for the #1 risk — cross-tenant data disclosure. Tenant context is derived server-side, enforced at the API (object-ownership check) and again in the database (row-level security). Neither layer trusts a client-supplied tenant id.
  • Row-Level Security on every tenant table, ENABLE + FORCE (even the table owner is policed), with a tenant_isolation policy: USING / WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid) — reads filter and writes are constrained to the acting tenant.
  • SET LOCAL app.tenant_id per transaction — transaction-scoped, so it is safe under PgBouncer transaction pooling (a session-level SET silently leaks across pooled clients; §7.3).
  • The app connects as a non-owner, non-superuser, non-BYPASSRLS role; migration lint asserts every tenant table has RLS enabled and a policy.
  • CI negative test (the Spec's provability requirement): seed tenants A and B; assert A cannot read/update/delete B's rows and cannot insert rows as B — at the SQL layer and through the API; any leak fails the build.
  • Spec-driven schema features: external_ref + per-tenant unique partial indexes on units/customers/leads/deals (import idempotency); append-only activities (audit) and consent_records (e-sign evidence) with UPDATE/DELETE revoked; customer address incl. state (per-state breach fan-out); retention_policies (legal floors vs the 2-year disposal default); the five unit date clocks + recon_cost/transport_cost; deal gross-input columns; export_batches/export_batch_items (accounting idempotency, §10).
  • Rental fleet (Spec §4–§6, App. D.5): rental_agreements carries the full contract state machine (reserved → on-rent → off-rent → in-inspection → closed, with off-rent and physical-return timestamps split so billing and liability end at different moments); rental_rates is the seasonal rate book; coi_records gates check-out on insurance expiry; inspections stores check-out/check-in evidence (meter readings, checklists, photos) plus the FMCSA annual inspection; units gain oec (dollar-utilization basis), rental_pool and annual_inspection_due; a partial unique index enforces one active agreement per unit; kpi_rentals materializes the fleet dashboard.
  • Self-host parity: same DDL; the single-tenant install keeps tenant_id columns (schema parity for upgrades) and may skip the policy block.

4.1 Contract-first interface definitions — beyond HTTP + JSON

Every client↔server surface gets a machine-readable contract, OpenAPI-style, even where the transport isn't request/response HTTP or the payload isn't JSON. The contracts are the source of truth: client SDKs, server validators, mock servers and the API reference all generate from them, so they cannot drift from the implementation. The suite:

SurfaceContract artifactWhat it covers
Request/response HTTPopenapi.yaml (OpenAPI 3.1)All 66 REST paths — including the non-JSON bodies: multipart/form-data photo & import uploads, text/csv error reports, text/csv / text/plain (IIF) accounting-export downloads
Outbound webhooksopenapi.yaml → top-level webhooks (an OpenAPI 3.1 feature)Events TPOS emits to a tenant's integration endpoints — unit.status_changed, deal.won, invoice.paid, lead.created — HMAC-signed, retried with backoff; distinct from the inbound /api/webhooks/* paths above

  • If a transport ever leaves HTTP entirely (e.g. a service is extracted with an RPC interface, or a message broker is introduced), the same discipline continues: AsyncAPI has first-class bindings for WebSocket, Kafka, MQTT and AMQP, and an IDL (e.g. Protobuf) would carry the RPC contract. Nothing about the approach assumes HTTP or JSON — only that every interface is contract-defined before it is implemented.
  • Single-source option: if maintaining parallel documents grows tedious, a meta-IDL such as TypeSpec (emits OpenAPI 3.1 + JSON Schema + Protobuf from one definition) or Smithy can become the single source that generates all of the above. Recommended only when the contract count grows — two hand-maintained documents don't yet justify the tooling.
  • CI gate: contracts are linted and diff-checked on every change (breaking-change detection), and the server's request/response validation is generated from them — the contract is the test oracle.

5 · Real-Time Updates

Requirements echoed. Spec §12: changes by one user — status, price, a new lead, an assignment, a payment — appear to others viewing the same data within ~1–2 seconds, without a manual refresh and without perceptible polling delay.
Server push, not client polling. Committed writes emit change events; a per-process fan-out pushes them to subscribed clients over one long-lived channel per session, topics scoped by tenant. The same events invalidate the materialized read models (§7.4).
  • Contract: the channel is formally defined in asyncapi.yaml (AsyncAPI 3.0) — servers, message schemas, resume semantics (§4.1).
  • Channel: one long-lived connection per signed-in client — SSE (GET /api/v1/events, text/event-stream) as the default for its simplicity/proxy-friendliness; upgradeable to WebSocket if bidirectional needs appear. A cursor query param replays missed events after a reconnect.
  • Feed: committed mutations write the activities row (already required for audit) and emit a change event — implementation options: Postgres LISTEN/NOTIFY (simple, fine at this scale) or logical-decoding/outbox if delivery guarantees must tighten. Events carry {topic, entity_type, entity_id, action, at} — clients re-fetch the entity through the normal (RLS-scoped) API rather than trusting payload data.
  • Scoping: topics are derived server-side from the session's tenant + role — the channel can never subscribe across tenants (same rule as §3).
  • Density interaction: thousands of long-lived connections favor an async runtime (§7.6) and are exactly why the API tier holds no per-request DB connection between events (§7.3).
  • UI behavior: lists/kanbans patch in place (a tile moves, a row updates, a badge increments); the storefront does not hold channels — its freshness comes from edge-cache invalidation on status change (§7.5).

6 · Frontend & UX

Requirements echoed. Spec §6 (twelve role workspaces over shared records), §7 (mobile-first, SEO-visible storefront), §12 (responsive phone → tablet → laptop → ultra-wide; WCAG 2.1 AA; field roles usable on a phone; dashboards < 2 s; real-time UI).

6.1 Recommendation — JS-first, with WASM where it earns its keep

  • UI stack: JS/TS. Next.js (React) as the default — or Django + htmx for the back office if the Django profile is chosen in §2. Rationale: the back office is forms-, tables- and CRUD-heavy, which is where the JS ecosystem's mature component libraries (data grids, date pickers, form kits) pay off daily; hiring is easiest; SSR for the storefront is first-class.
  • Storefront: DOM-rendered SSR + edge cache (§7.5) — the public site must be crawlable and fast on a phone; canvas-rendered approaches are ruled out by SEO/accessibility alone.
  • Rust→WASM as modules, not the whole app: the derived-field formula engine (Spec Appendix D — margins, aging, commissions) is a natural WASM module: pure, correctness-critical, shared verbatim between server and client so previews always match bookings.
  • Responsive strategy: one responsive web app (no separate native build in Phase 1 — see the Bid Pack); layouts collapse from the ultra-wide dashboard grid → laptop → tablet two-pane → phone single-pane with bottom navigation; recon & delivery screens are touch-first since they're used in the yard; WCAG 2.1 AA with full keyboard navigation.

6.2 The Rust/WASM alternative — assessed honestly

If the build team is Rust-first by conviction, the only whole-app WASM options that preserve SEO/accessibility are the DOM-rendered frameworks — Leptos (web-first: SSR, islands, fine-grained signals, the strongest Rust web story) or Dioxus (one codebase across web/desktop/mobile; React-like). Choose Leptos for this product if at all — the storefront is a web/SSR problem. Accept the trade-offs: component ecosystems are young (Thaw UI / headless primitives + Tailwind, no AG-Grid-class data grid), APIs move fast, and the hiring pool is small. Canvas-rendered stacks (egui, Flutter Web) are not acceptable for the storefront or the accessible back office.

6.3 Data tables & filtering — server-side by design

No framework choice changes this: with tens of thousands of rows per tenant, filtering/sorting/pagination belong in the API and SQL, not the browser. Every list endpoint takes ?q=&status=&sort=&page=&limit= (already in openapi.yaml); the table component stays "dumb" and renders a page; the filter UI (facet chips, date ranges, saved views) is bespoke in any stack. This sidesteps the one place the Rust UI ecosystem is furthest behind (rich client-side data grids) and keeps payloads small on yard Wi-Fi.

7 · Performance & Scaling

Requirements echoed. Spec §12: interactive actions feel instant; dashboards < 2 s; maximize simultaneous active users per server; hundreds+ tenants and tens of thousands of units/leads per tenant with no per-tenant degradation; 99.9% availability with a cache-served storefront.

TPOS is database-bound CRUD: requests spend their time waiting on Postgres, not on application code. The performance and tenant-density wins therefore live in the data layer and the connection pool, not in an exotic runtime or premature sharding. This appendix is one optimization profile; apply it only to the degree the product needs.

Define the dimension first. "High performance" is not one thing, and the lever order changes with it. Decide which of these dominates before optimizing — over-investing in the wrong one is wasted complexity.
If the goal is…Dominant levers, in order
p99 read latency (dashboards feel instant)Materialized read models → cache hot reads → tenant_id-leading indexes → read replicas
Write / transaction throughputIndex discipline → prepared statements & batching → hash-partition hot tables → pool sizing

7.1 Indexing & query design — the foundation (and what makes RLS cheap)

  • Every hot index leads with tenant_id, then the query's predicates: (tenant_id,status), (tenant_id,stock_no), (tenant_id,due_at), (tenant_id,stage), etc.
  • Keep Row-Level Security. With the right composite index the planner pushes the policy predicate into the index scan, so RLS is cheap (reported order-of-magnitude: ~0.3 ms policy evaluation at 50 M rows / 10 K tenants; ~1–5% vs. app-level filtering). The 100× penalty comes from a missing tenant_id-leading index, not from RLS itself. Database-enforced isolation is worth the few percent — one cross-tenant leak is existential, and it protects you even when application code has a bug.
  • Eliminate N+1s; use prepared statements; keep working sets index-resident.

7.2 Partitioning — secondary, and use HASH not list

  • Partitioning is a lever only for the largest tables (e.g. activities, units at very high volume); the composite index above does most of the work first.
  • With thousands of tenants, partition by HASH(tenant_id) into a fixed number of partitions (e.g. 16–64) for cache locality and scan pruning. Do NOT list-partition one-per-tenant — thousands of partitions blow up planner time and DDL. Time-range sub-partitioning suits the audit log.

7.3 Connection pooling — the real density lever

  • Postgres is process-per-connection (~5 MB + context-switch per connection), so density comes from PgBouncer in transaction-pooling mode multiplexing many clients onto a small pool sized to roughly 3–5 backend connections per CPU core.
  • Gotcha that interacts with RLS: under transaction pooling a session-level SET app.tenant_id does not persist across statements. Set the tenant per-transaction with SET LOCAL app.tenant_id = … (or set_config('app.tenant_id', …, true)) so RLS still applies. Also avoid session-scoped prepared-statement / session-feature assumptions in transaction mode.

7.4 Read path — precompute the dashboards (CQRS-lite)

  • The KPI dashboards (§9) aggregate across many rows. Precompute them into materialized views / rollup tables refreshed incrementally by the background worker, so a dashboard load is an O(1) indexed read, not a per-request fan-out join. This is the single biggest internal-latency win.
  • Cache hot reads (Redis / Dragonfly or in-process) with event-driven invalidation on writes; route all dashboard/report traffic to read replicas.

7.5 Storefront at the edge

The public storefront's "available inventory" is the highest-volume, most cacheable traffic. Serve it from a CDN / ISR edge, invalidated when a unit's status changes. This removes the largest read load from the origin entirely and is often the cheapest way to raise effective tenants-per-server.

7.6 Runtime — a minor lever for DB-bound work

Framework benchmarks show per-request gaps collapse once Postgres is in the loop (compiled runtimes dominate only the compute-bound plaintext/JSON rounds). For DB-bound CRUD you will not get throughput from switching language — choose the runtime for its concurrency model and your team, not per-query speed. Where it touches density: an async / light-concurrency runtime (Go, .NET, Node, or Elixir for connection-heavy/real-time) holds more in-flight requests per box than a process-per-worker Python/Ruby setup. Rust is not required here and its productivity cost rarely pays back on this workload.

7.7 Scaling ladder — earn each step

  1. Vertical scaling + PgBouncer (handles a large share of workloads on its own).
  2. Add read replicas for the read/report load.
  3. Hash-partition the few largest tables.
  4. Only once a single primary is genuinely exhausted (commonly hundreds of GB+), shard with Citus co-located by tenant_id. Keep the schema partition-ready (tenant_id on every table) so this migration is cheap — but defer it; vanilla Postgres + replicas goes much further than teams expect.
Caveat — treat the numbers as order-of-magnitude. The RLS timing figures come from a single practitioner benchmark and the single-node size thresholds are partly vendor framing. Use them for intuition; benchmark on your own schema, queries and data before treating any figure as a constant. Sources: practitioner RLS-at-scale benchmarks, PgBouncer pooling guides (connection-cost & per-core sizing), single-node-Postgres scaling write-ups, and the TechEmpower framework benchmarks (database-query rounds).

8 · Security Mechanisms

Requirements echoed. Spec Appendix B.5 states the security outcomes (isolation, hardened sessions, strong password storage, MFA, throttling, token hygiene, CSRF defense, secrets, encryption, immutable audit, rate limits, validated uploads, SSRF restraint). These are the proposed mechanisms.

Identity & sessions

  • Passwords: Argon2id (m = 19 MiB, t = 2, p = 1); bcrypt ≥ 10 accepted for legacy migration only.
  • Cookies: HttpOnly + Secure + SameSite, __Host- prefix; session id ≥ 64-bit entropy; rotate on login; idle + absolute timeouts; server-side logout.
  • MFA (TOTP/WebAuthn) — required for admin, titles and payment-touching roles.
  • Login throttling + lockout; reset tokens single-use, time-limited, no account enumeration.
  • Portal/API tokens: short-lived, role-scoped, signature/issuer/audience/expiry all validated.
  • CSRF: synchronizer token (or HMAC double-submit) on cookie-auth routes; custom-header requirement on the bearer API.

Platform & data

  • Isolation mechanism per §3 (RLS FORCE, SET LOCAL, non-owner role, CI negative test).
  • Authorization: RBAC (role → permission sets, the Spec §10 matrix) layered over ABAC (tenant id + field sensitivity) with field-level masking of PII / title / payment data. Users hold a role set; effective permissions are the union, lot scope intersects, and a separation-of-duties check blocks self-approval (Spec §10 “Multi-role users”).
  • Secrets in a managed KMS/secret store; never in VCS; DB + token-signing keys rotated.
  • TLS in transit; encrypted volumes at rest; column-level encryption/tokenization for payment tokens & sensitive PII (only token + last4 + brand are ever stored — §9).
  • Audit: append-only activities (UPDATE/DELETE revoked) with actor, action, entity, timestamp.
  • Rate limits per IP / token / tenant on auth, API, upload. Server-side validation + parameterized queries everywhere.
  • Uploads: magic-byte content verification (never trust Content-Type), randomized names, object storage off-webroot, malware scan, image re-encode.
  • SSRF: server-side fetches allow-listed; RFC1918 / link-local / metadata addresses blocked; resolved IP validated.

The compliance regime these mechanisms serve (GLBA Safeguards Rule, breach reporting, ESIGN, retention) is specified — with citations — in Spec Appendix B; the annual pen test + vulnerability-assessment cadence it requires is carried as a delivery line in the Bid & Delivery Pack.

Target-agnostic canonical export model with per-target adapters — the no-rewrite seam. Targets become pluggable serializers (the same architecture a unified-API vendor hosts internally), turning N² point-to-point translators into ~2N. File adapters ship first and are permanent infrastructure, since QuickBooks Desktop has no clean REST API.
  • Canonical model: a thin, export-only representation — balanced journal entries (debit/credit lines → mapped GL accounts) plus customer / invoice / payment / tax-rate and a generic "segment" dimension (maps to QBO classes or Xero tracking categories later).
  • v1 — file adapters (ships first): manual, on-demand summary journal-entry export as CSV (QuickBooks Online) and IIF (Desktop). Needs no OAuth and no Intuit production review; sidesteps QBO's invoice-CSV sales-tax block and 100-row cap. Trade-off accepted: GL-accurate books, but no invoice-level AR aging inside QuickBooks until the API phase.
  • GL mapping wizard (one-time, per dealer): map system buckets — trailer revenue, COGS, AR, sales-tax payable, fees, customer deposits — to the dealer's own accounts (GET/PUT /api/v1/accounting/mapping). File targets need exact account-name matches; the API target resolves and stores QuickBooks Account Ids.
  • Idempotency: every run creates an export_batch; exported records are marked via export_batch_items so a re-run never re-emits them. On the API path, the invoice number becomes QuickBooks DocNumber + query-before-insert (QuickBooks has no native idempotency key).
  • Rental money (ASC 842 lessor accounting). Operating-lease rental income is recognized straight-line over the term (ASC 842-30-25-11) while the unit stays in fleet PP&E and depreciates — so the canonical export model carries the rental GL buckets (Rental Revenue, Fleet Depreciation, Fleet Maintenance, Customer Deposits, Deferred/Accrued Rent) alongside the sale set. Variable charges (mileage overage, damage) recognize in the period incurred; security deposits are liabilities until applied or refunded (Indianapolis Power & Light); card pre-auth holds are not money received and post no GL entry. An RPO becomes a sales-type lease when exercise is “reasonably certain” (ASC 842-10-25-2) — the system then derecognizes the unit, recognizes selling profit, and switches remaining income to interest; that conversion is an explicit, audited workflow step. Sales tax computes per recurring invoice with contract duration and equipment class as inputs (e.g. Texas taxes trailer rentals at 10% ≤30 days / 6.25% to 180 days under motor-vehicle gross-rental rules, and several states changed regimes mid-2025) — jurisdiction tables, per the Spec.
  • Phases 2–4 (triggered by demand, sized in the Bid Pack): QBO REST-API push (OAuth2 + Intuit review) → Web Connector/qbXML for Desktop detail → additional systems via new adapters, or a unified-API aggregator once targets exceed ~2.

11.1 What we changed our minds about (and why)

Three decisions from the first "performance-first" pass were corrected once benchmark evidence was reviewed — recorded here so the reasoning is auditable, not lost:

  • #8 — Rust is not the lever. For DB-bound CRUD, runtime choice barely moves throughput; the language win is real only on compute-bound paths. [9]
  • #9 — Don't drop RLS for speed. The cost is the missing tenant_id-leading index, not the policy; keep DB-enforced isolation. [2][3]
  • #10 — Don't shard early. A single Postgres primary + replicas + partitioning goes much further than expected; defer Citus. [5][6]
