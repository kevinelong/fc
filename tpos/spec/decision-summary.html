TPOS — Architecture Decision Summary

Trailer Portal Operating System · one-page front-sheet for the full Product Specification · pairs with schema.sql + openapi.yaml

The shape of the system

A multi-tenant B2B SaaS: independent trailer-resale dealerships sign up and run their whole operation — inventory, leads, deals, quotes, reconditioning, titles, invoicing, delivery, and a public storefront — on one shared platform. One trailer record is viewed through many role lenses (inventory item → deal → work order → invoice → title → delivery → public listing). Sold three ways: monthly hosted, annual license, or one-time perpetual purchase.

Headline decisions & why

DatabasePostgreSQL, single primary + read replicas. Relational integrity, mature tooling, RLS for tenant isolation. No need for NoSQL — the domain is relational.
Tenant isolationShared schema + Row-Level Security (tenant_id column, tenant_isolation policy). RLS overhead is ~1–5% when indexes lead with tenant_id; the missing index — not RLS — is the 100× penalty.
App architectureModular monolith behind one API, split into modules (sales, inventory, service, billing, storefront). Microservices add ops cost we don't need at this scale; the module seams let us extract later if a service earns it.
Connection poolingPgBouncer in transaction mode; set the tenant with SET LOCAL app.tenant_id per transaction. Session-level SET leaks across pooled clients — SET LOCAL is the density lever (~3–5 conns/core).
Reads / reportingMaterialized read models (KPI views) refreshed on a schedule; CQRS-lite. Dashboards stay fast without taxing the write path.
StorefrontEdge-cached static-first public pages reading a published-inventory view. Buyer traffic never touches the operational DB hot path.
Scaling nextHash-partition the largest tables by tenant_id into a fixed partition count; add replicas. Single-node Postgres + partitioning + replicas goes very far.

Reference stack (illustrative)

Datastore PostgreSQL 16 · RLS · PgBouncer
API One service — Django/DRF or NestJS
Auth Session cookie (staff) + bearer (API/portal)
Storefront Static/SSR, CDN-cached
Storage Object store for photos/docs
Async Queue for email, soft-pulls, exports

The spec is implementation-agnostic — language & framework are the rebuilder's choice. These are the load-bearing constraints, not mandates.

Roads not taken

Citus / shardingDeferred — premature at launch scale; revisit past single-node limits.
DB-per-tenantMigration & connection sprawl; RLS gives isolation more cheaply.
MicroservicesOps & distributed-txn cost unjustified now; monolith first.
Rust/Go for speedRuntime rarely the bottleneck for DB-bound CRUD; DB & pooling dominate.
