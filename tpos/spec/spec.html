Executive Overview

TPOS is a multi-tenant vertical SaaS that runs an independent trailer dealership’s entire operation — its public storefront and its whole back office — on one shared record of truth, where a single trailer is seen through 12 role lenses (inventory → deal → work order → invoice → title → delivery → listing). Sold hosted (monthly), licensed (annual), or self-hosted (one-time). The Phase-1 MVP is ≈ 6–12 months across 5 delivery stages (demo → GA).

The product

  • Who: small-to-mid used/refurbished commercial-trailer dealers, replacing a website builder + CRM + spreadsheets + QuickBooks + listing sites with one role-aware platform.
  • Core loop: acquire → recondition → price → list → lead → quote → finance → title → deliver → book — each stage hands the same record to the next role.
  • Pricing: Hosted $199–$1,290/mo · annual license · one-time self-host.

1 · Product Vision & Business Model

TPOS is a vertical SaaS that gives an independent trailer dealership one system to run both its public storefront and its entire back office — acquisition, reconditioning, pricing, marketing, sales, financing, titling, delivery and bookkeeping — on a single shared record of truth.

The market is fragmented small-to-mid dealers (used & refurbished commercial trailers: dry vans, flatbeds, reefers, lowboys, dumps, tankers, chassis) who today stitch together a website builder, a generic CRM, spreadsheets, QuickBooks and listing sites (TruckPaper, Facebook). TPOS replaces that stack with a purpose-built, role-aware platform.

The platform operator (TPOS, Inc.) additionally runs a super-admin control plane to provision tenants, meter usage, bill subscriptions, and support dealers (see §6.12).

Product principles

  • One record, many lenses. A trailer is simultaneously inventory, a deal, a work order, an invoice line, a title file, a delivery, and a public listing. Every role edits the same entity through a view shaped to its job — never a copy.
  • The storefront is generated, not separate. Inventory marked available is automatically published to the dealer's branded public site and syndicated to listing channels.
  • Role-first, not module-first. Each user lands on a workspace built around their daily goals and decisions, not a generic menu of tables.
  • Auditable by default. Price changes, discounts, status transitions and money movement are logged with who/when/why.

13 · Acceptance Criteria

The rebuild is "done" when the following end-to-end scenarios pass for a tenant, with figures reconciling across roles:

  1. Acquire→list. Inventory Manager adds an incoming unit; Service completes intake & recon; Pricing sets list/floor; status flips to available and the unit appears on the storefront and syndication.
  2. Lead→quote. A storefront "Request a quote" creates a Lead in the Lead Desk within seconds, routes to a salesperson, who builds a Quote tied to the unit.
  3. Negotiate→approve. A below-floor offer requires Sales Manager approval, which is logged; the Deal advances to financing.
  4. Finance→title→deliver. Customer applies for financing in the portal and sees status; Office tracks title to "in hand"; Dispatch schedules and tracks delivery to "delivered."
  5. Book. Bookkeeper issues the invoice, records payment, and the sale appears in revenue/gross KPIs that match the Owner dashboard.
  6. Operate (hosted). Super-Admin provisions a new tenant, sees it billed, and watches MRR/usage update.

Appendix C · Performance & Scaling

TPOS is database-bound CRUD: requests spend their time waiting on Postgres, not on application code. The performance and tenant-density wins therefore live in the data layer and the connection pool, not in an exotic runtime or premature sharding. This appendix is one optimization profile; apply it only to the degree the product needs.

Define the dimension first. "High performance" is not one thing, and the lever order changes with it. Decide which of these dominates before optimizing — over-investing in the wrong one is wasted complexity.
If the goal is…Dominant levers, in order
p99 read latency (dashboards feel instant)Materialized read models → cache hot reads → tenant_id-leading indexes → read replicas
Write / transaction throughputIndex discipline → prepared statements & batching → hash-partition hot tables → pool sizing
Tenants per server (density)PgBouncer transaction pooling → edge-offload the storefront → shared-schema low footprint → async runtime

C.1 Indexing & query design — the foundation (and what makes RLS cheap)

  • Every hot index leads with tenant_id, then the query's predicates: (tenant_id,status), (tenant_id,stock_no), (tenant_id,due_at), (tenant_id,stage), etc.
  • Keep Row-Level Security. With the right composite index the planner pushes the policy predicate into the index scan, so RLS is cheap (reported order-of-magnitude: ~0.3 ms policy evaluation at 50 M rows / 10 K tenants; ~1–5% vs. app-level filtering). The 100× penalty comes from a missing tenant_id-leading index, not from RLS itself. Database-enforced isolation is worth the few percent — one cross-tenant leak is existential, and it protects you even when application code has a bug.
  • Eliminate N+1s; use prepared statements; keep working sets index-resident.

C.2 Partitioning — secondary, and use HASH not list

  • Partitioning is a lever only for the largest tables (e.g. activities, units at very high volume); the composite index above does most of the work first.
  • With thousands of tenants, partition by HASH(tenant_id) into a fixed number of partitions (e.g. 16–64) for cache locality and scan pruning. Do NOT list-partition one-per-tenant — thousands of partitions blow up planner time and DDL. Time-range sub-partitioning suits the audit log.

C.3 Connection pooling — the real density lever

  • Postgres is process-per-connection (~5 MB + context-switch per connection), so density comes from PgBouncer in transaction-pooling mode multiplexing many clients onto a small pool sized to roughly 3–5 backend connections per CPU core.
  • Gotcha that interacts with RLS: under transaction pooling a session-level SET app.tenant_id does not persist across statements. Set the tenant per-transaction with SET LOCAL app.tenant_id = … (or set_config('app.tenant_id', …, true)) so RLS still applies. Also avoid session-scoped prepared-statement / session-feature assumptions in transaction mode.

C.4 Read path — precompute the dashboards (CQRS-lite)

  • The KPI dashboards (§9) aggregate across many rows. Precompute them into materialized views / rollup tables refreshed incrementally by the background worker, so a dashboard load is an O(1) indexed read, not a per-request fan-out join. This is the single biggest internal-latency win.
  • Cache hot reads (Redis / Dragonfly or in-process) with event-driven invalidation on writes; route all dashboard/report traffic to read replicas.

C.5 Storefront at the edge

The public storefront's "available inventory" is the highest-volume, most cacheable traffic. Serve it from a CDN / ISR edge, invalidated when a unit's status changes. This removes the largest read load from the origin entirely and is often the cheapest way to raise effective tenants-per-server.

C.6 Runtime — a minor lever for DB-bound work

Framework benchmarks show per-request gaps collapse once Postgres is in the loop (compiled runtimes dominate only the compute-bound plaintext/JSON rounds). For DB-bound CRUD you will not get throughput from switching language — choose the runtime for its concurrency model and your team, not per-query speed. Where it touches density: an async / light-concurrency runtime (Go, .NET, Node, or Elixir for connection-heavy/real-time) holds more in-flight requests per box than a process-per-worker Python/Ruby setup. Rust is not required here and its productivity cost rarely pays back on this workload.

C.7 Scaling ladder — earn each step

  1. Vertical scaling + PgBouncer (handles a large share of workloads on its own).
  2. Add read replicas for the read/report load.
  3. Hash-partition the few largest tables.
  4. Only once a single primary is genuinely exhausted (commonly hundreds of GB+), shard with Citus co-located by tenant_id. Keep the schema partition-ready (tenant_id on every table) so this migration is cheap — but defer it; vanilla Postgres + replicas goes much further than teams expect.
Caveat — treat the numbers as order-of-magnitude. The RLS timing figures come from a single practitioner benchmark and the single-node size thresholds are partly vendor framing. Use them for intuition; benchmark on your own schema, queries and data before treating any figure as a constant. E.5 Controls checklist (hard gates)

Tenant isolation — the #1 risk

  • App connects as a non-owner, non-superuser, non-BYPASSRLS role.
  • FORCE ROW LEVEL SECURITY on every tenant table.
  • SET LOCAL app.tenant_id per transaction — never session SET under PgBouncer transaction pooling.
  • WITH CHECK (tenant_id = …) on every write policy (block insert-as-wrong-tenant).
  • Migration lint: every tenant table has RLS enabled and a policy.
  • Derive tenant_id from session/token server-side; never from a client param (OWASP API #1, BOLA/IDOR). UUID resource ids.
  • CI negative test: tenant A cannot read / update / delete / insert-as tenant B — at the DB and API layer; fail the build on any leak.

AuthN / AuthZ (OWASP ASVS)

  • Cookies: HttpOnly, Secure, SameSite, __Host- prefix; session id ≥ 64-bit entropy; regenerate on login; idle + absolute timeouts; server-side logout.
  • Passwords: Argon2id (m=19 MiB, t=2, p=1); bcrypt ≥ 10 only for legacy.
  • MFA; login throttle/lockout; safe reset (single-use, time-limited, no enumeration).
  • Tokens: short-lived, scoped, signature/issuer/audience/expiry validated.
  • CSRF: synchronizer or HMAC double-submit for cookie auth; custom header on the bearer API.
  • RBAC (roles → permission sets) over ABAC (tenant_id + field sensitivity).

Cross-cutting

  • Secrets in a managed KMS/secret store, never in VCS; rotate DB & token-signing keys.
  • TLS in transit; encryption at rest for DB + object storage; column encryption / tokenization for payment tokens & PII.
  • Immutable, append-only audit log (the Repudiation control).
  • Rate limiting per IP / token / tenant on auth, API and upload.
  • Server-side input validation & parameterized queries everywhere.
  • Secure upload: magic-byte (not Content-Type) validation, UUID filenames, off-webroot, malware scan, image re-encode.
  • SSRF allow-listing on any server-side URL fetch (block RFC1918 / link-local / 169.254.169.254; validate resolved IP).

I.3 GL mapping & idempotency (required for every path)

  • Chart-of-accounts mapping wizard (one-time, per dealer). Map TPOS buckets — trailer revenue, COGS, AR, sales-tax payable, processing fees, customer deposits — to the dealer’s own QuickBooks accounts. The QBO API references accounts by AccountRef (the QB Account Id), so the wizard must resolve and store those ids; for CSV/IIF the account names must match exactly or rows fail/misroute. Reject postings into a closed/locked period.
  • Duplicate prevention. QuickBooks has no built-in idempotency key on create; re-export re-posts. Use the TPOS invoice number as DocNumber (unique), store the returned QB Id, and query-before-insert (update, don’t duplicate) on the API path. For file exports, stamp each record with its export batch + date so the bookkeeper is never handed the same rows twice — files have no platform-side dedupe.

I.4 Recommendation

Ship v1 as a manual, on-demand summary journal-entry export delivered as a downloadable file (CSV for Online, IIF for Desktop), driven by the one-time GL-mapping wizard. Then QBO Accounting-API “click-to-push” batch (Phase 2), Web Connector/qbXML for Desktop detail (Phase 3), and defer a unified-API aggregator until multiple targets or automated sync justify it (Phase 4). Why: a downloaded file needs no OAuth and no Intuit production review, so it ships now; the summary JE dodges the CSV sales-tax block and invoice cap and imports cleanly into both products; and the account-mapping table + batch/dedupe stamping built for v1 are exactly what the API phase reuses. The decision knobs for what comes next: number of targets (1–2 → file/direct; 3+ → aggregator economical), manual vs automated, cost sensitivity (aggregators are quote-only / per-connection), and the measured Online-vs-Desktop ratio in the real dealer base.
